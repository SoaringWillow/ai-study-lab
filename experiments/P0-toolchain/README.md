## 这个项目在练什么

不是练写代码，是练三个动词里的前两个：**读 → 跑**。

后面 P1–P5 每次卡住，九成不是概念不懂，是环境、路径、形状、显存。P0 就是专门把这一类卡点提前吃掉的地方。所以它的交付物不是「跑通了」这个结果 —— 是**踩坑日志**：错误 → 真实原因 → 解法。跑通了但日志是空的，这个项目算没做。

## 为什么这里不给命令

这份 README 故意**不写具体命令**。ENGINEERING.md 第一节已经给了那套固定套路（uv venv → editable install → 跑 README 里最小的那个命令），剩下的每个坑都得自己踩 —— 别人替你查掉的报错，练不出任何东西。

同理，**报错先自己读 60 秒**再问 AI（ENGINEERING.md 第二节）。日志里专门有一列记这个时长，是为了让这条规则可被自己审计。

## 三个仓库（按这个顺序，每个考一类失败）

| # | 仓库 | 它考的是哪类坑 | 什么算「跑通」 | 时间盒 |
|---|---|---|---|---|
| 1 | **karpathy/micrograd** | 最干净的一个：纯 Python、无 GPU、无数据集。如果这个都卡住，问题在环境隔离本身 | demo notebook 跑完，能看到 loss 下降的那串数字 | 1h |
| 2 | **一个 MuJoCo demo**（`mujoco` 官方示例或 `mujoco_menagerie` 里任一模型） | 二进制依赖与渲染：headless 环境、EGL/OSMesa、显示后端 —— 这类坑和 Python 包管理完全无关 | 仿真跑起来，能打印出某个时刻的关节角或者存下一帧图 | 2h |
| 3 | **huggingface/lerobot** quickstart | 真实研究仓库的全套：大依赖树、数据集下载、GPU/显存、版本漂移。前两个是热身，这个才是本体 | quickstart 里第一个评估或训练命令出第一个数字（不需要跑完） | 4h |

**时间盒到了还没通，就停下来记录状态，第二天接着来。** 卡住的过程本身就是交付物 —— 别为了「跑通」去抄一个能用的 conda 环境，那等于把这次训练作废。

顺序是有理由的：1 隔离环境 → 2 系统依赖 → 3 研究仓库的全部复杂度。倒过来做会在第一天就被一个 CUDA 报错埋掉，然后分不清是哪一层的问题。
